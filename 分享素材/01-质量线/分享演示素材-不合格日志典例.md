## 典例 1：跨进程 zmq raise 无前置日志（P0，最高频）

**扫描数据**：vllm-ascend 仓 **3 处**，全部集中在 `distributed/kv_transfer/kv_p2p/`（mooncake_*_connector）。

### 坏写法（代码）

```python
# distributed/kv_transfer/kv_p2p/mooncake_layerwise_connector.py:1974
raise zmq.ZMQError("Receive timeout")

# distributed/kv_transfer/kv_p2p/mooncake_connector.py:1853
raise zmq.ZMQError("Receive timeout")

# distributed/kv_transfer/kv_p2p/mooncake_hybrid_connector.py:1858
raise zmq.ZMQError("Receive timeout")
```

### 现场日志里你看到什么

- **vllm 进程日志**：只有 `zmq.ZMQError: Receive timeout`，**无对端 IP、无超时配置、无 recv 计数**。
- **引擎侧**：`EngineCoreReq` RPC 超时报错，调用方只看到 `RPC timed out`。
- **排障困境**：不知道是 Mooncake 主从哪台挂了、timeout 配的多少、网络有没有丢包——只能猜「是不是 Mooncake 集群问题」。

### 不合格原因

| 维度 | 问题 |
|------|------|
| 分级/可见性 | 失败语义只进了 Python 异常，**没进服务端 ERROR 日志** |
| 描述 | 无 peer/timeout_ms/recv_count/errno |
| 组件 | 无 `[vllm/kv_transfer]` 等归属 |
| 下一步 | 无「查对端进程 / 查网络丢包 / 查 timeout 配置」指引 |

### 建议改法（好写法示意）

```python
logger.error(
    "[vllm/kv_transfer] Mooncake receive timeout. "
    "peer=%s timeout_ms=%s recv_count=%s errno=%s. "
    "可检查：1. 对端 mooncake 进程是否存活 2. 网络丢包率 3. timeout_ms 配置是否合理",
    peer, timeout_ms, recv_count, errno,
)
raise zmq.ZMQError(...)
```

### 讲一句

> 跨进程的失败不是没发生，是**对端信息没写进我们能 grep 的日志**；加一行 error + 4 个关键字段，就能从「无痕超时」变成「可定位节点级事件」。

## 典例 2：业务中断 RuntimeError 缺关键参数（P1，最严重）

**扫描数据**：vllm-ascend 仓 **61 处**，按模块分布：model_loader 14 / _310p 12 / distributed 9 / cpu_binding 8 / worker 4 / device 4。

### 坏写法（代码）

```python
# model_loader/netloader/interaction/elastic.py:178
raise RuntimeError(f"Send data {data} to server fails, detail: {e}")
# 缺：server_addr、retry_count、data 大小

# cpu_binding.py 8 处：
raise RuntimeError(f"Failed to bind CPU for rank {rank}")
# 缺：npu_id、cpuset 范围、失败原因细分
```

### 现场日志里你看到什么

- elastic.py 报「Send data 失败」——**不知道是哪台 server、data 多大、是不是第一次失败**。
- cpu_binding.py 报「bind CPU 失败」——**不知道是哪个 rank 哪个 npu、cpuset 范围是什么、是不是被占用**。
- 现场翻日志只能定位到大致文件，**根因得靠人肉试**（改 rank 重试、改 cpuset 重试）。

### 不合格原因

- 异常把"业务中断"信息塞进了 `RuntimeError`，但**所有可定位字段都在格式化字符串外丢失**。
- 扫描报告归类：业务中断 RuntimeError **61 处** + 启动期 ValueError **2 处** + 超时 **1 处** = P1 合计 64 处。

### 建议改法

```python
logger.error(
    "[vllm/model_loader] NetLoader elastic send data to server failed. "
    "server_addr=%s data_size=%s retry_count=%s last_error=%s. "
    "可检查：1. server 是否存活 2. 网络是否可达 3. data 大小是否超限",
    server_addr, len(data), retry_count, str(e),
    exc_info=True,
)
raise RuntimeError(...) from e
```

### 讲一句

> RuntimeError 把"业务中断"信号告诉你了，但**没告诉你中断在哪台机器、哪条数据、第几次重试**——专家路径里这里必须 **error + exc_info + 4 个关键字段**。

## 典例 3：入参校验打 raise/ERROR（级别误用）

**扫描数据**：vllm-ascend 仓 **122 处** P2（应改 WARNING），其中入参校验 ValueError 104 处、RuntimeError 10 处。

### 坏写法（代码）

```python
# model_loader/netloader/executor/netloader_pg.py:65
raise RuntimeError("world_size must be positive")
```

### 现场日志里你看到什么

```
ERROR ... world_size must be positive
```

- 运维告警按 ERROR 聚合 → **误报风暴**。
- 实际是配置 world_size 填了 0 或负数，**不阻断其他正常请求**（多数情况下会 fallback 或直接退出），应是 WARNING 或启动期一次性提示。

### 扫描数据细节

- **入参校验 ValueError 104 处**（worker 22、distributed 22、ops 18、eplb 9、_310p 7 等）
- **入参校验 RuntimeError 10 处**（netloader 校验 world_size/rank、scheduler 校验 request.status、causal_conv1d 校验 x.shape 等）
- **其他 6 处**（含弃用警告 2 处）

### 建议改法

```python
logger.warning(
    "[vllm/model_loader] Invalid world_size. value=%s expected>0 "
    "fallback=use_default_1 check=config.world_size",
    world_size,
)
# 保留 raise 也可，但必须前置 warning 让告警不触发
```

### 讲一句

> 级别不是「看起来像错就 ERROR」——**会不会阻断业务、要不要半夜叫醒人**，才决定 WARNING 还是 ERROR。122 处入参校验 raise = 122 个潜在的告警噪音源。

## 典例 4：纯静态短句（分享背景页首选对比）

**扫描数据**：vllm-ascend 仓 **116 条**纯静态 ERROR/WARNING，集中在 netloader（25+）、rfork（12+）、kv_transfer（25+）、worker（5+）、其他（~30）。

### 坏日志（现场输出）

```
ERROR ... Failed to load model
```

或：

```
ERROR ... CONFIG_FILE not found
```

### 好日志（改后现场输出）

```
ERROR [vllm/model_loader] Failed to load model. model_path=/data/models/qwen2-72b
retry_count=3 last_error=out of memory required=48GiB available=32GiB
next=1. check model_path exists 2. check NPU memory 3. reduce max_model_len
```

### 5 个典型样本（来自报告 §4.1）

| 文件:行号 | 坏日志 | 缺什么 |
|----------|--------|--------|
| `model_loader/netloader/load.py:69` | `Failed to load model` | model_path、error、retry_count |
| `model_loader/netloader/netloader.py:69` | `CONFIG_FILE not found` | config_path、env var name、fallback 行为 |
| `model_loader/netloader/netloader.py:273` | `NetLoader elastic loads model fails` | rank、load_time、最后错误、是否 fallback |
| `model_loader/rfork/rfork_loader.py:186` | `logger.warning(...)` | 内容未知（按文件读） |
| `worker/worker.py:799` | `query NPU card %s timeout.` | **级别错**：实际 INFO 却含 timeout，应改 WARNING |

### 对照表（可贴 PPT）

| 维度 | 坏日志 | 好日志 |
|------|--------|--------|
| 组件 | 无 | `[vllm/model_loader]` |
| 关键参数 | 无 model_path/error | model_path、retry_count、last_error、内存数 |
| 原因 | 仅「failed」 | 具体 OOM/文件不存在/超时 |
| 下一步 | 无 | `next=check model_path...` 3 条可执行项 |

### 坏写法（代码示例）

```python
# model_loader/netloader/load.py:69
logger.error("Failed to load model")
# → 缺：model_path、error、retry_count
```

### 讲一句

> 坏日志只回答「失败了」；好日志回答「**谁、对谁、什么错、下一步查哪**」——定位时间差一个数量级。116 条静态短句是 vllm-ascend 最大的描述问题。

## 典例 5：全仓无统一组件标识（系统性）

**扫描数据**：

- 源码中含 `[vllm/xxx]` 字符串的 logger：**0/601 (0%)**
- 仅有零星手动前缀：`[cpu_bind_mode]`、`[migrate]`、`[irq]`（在 cpu_binding.py 内部约 4 处）
- **报告 §5.1 评价**：严重

### 现场表现

- 推理失败 grep `ERROR` in kv_transfer：217 条日志混在一起，**不知道先找 distributed / model_loader / worker 哪个组**。
- 跨模块问题（如「kv_transfer 调 mooncake 失败 + model_loader 加载慢」）无法拆开看。

### 建议改法（规范级，一条示例）

```python
# 统一前缀：仓库/模块
logger.error("[vllm/kv_transfer] ...")
logger.warning("[vllm/model_loader] ...")
logger.info("[vllm/worker] ...")
```

### 讲一句

> 组件标识是日志的「收件人地址」——没有它，scan 能扫出问题，但**人仍不知道找谁改**。vllm-ascend 全仓 0% 覆盖率 = 整个仓的日志「没有收件人」。
